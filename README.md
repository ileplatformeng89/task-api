# Tasks API

Modern REST API for task management built with FastAPI, SQLAlchemy,
PostgreSQL, Alembic, Docker Compose, and uv.

## Stack

-   Python 3.14
-   FastAPI
-   Pydantic
-   SQLAlchemy 2
-   PostgreSQL 17
-   Alembic
-   uv
-   pytest + pytest-cov
-   Ruff
-   Docker / Docker Compose

## Architecture

``` text
Client
  |
  v
FastAPI Router
  |
  v
Service Layer
  |
  v
SQLAlchemy
  |
  v
PostgreSQL
```

The project separates HTTP routing, validation schemas, business logic,
persistence models, and database configuration.

## Local Development

### Prerequisites

You need:

-   Docker
-   Docker Compose
-   GNU Make

`uv` is used inside the application image, so it is not required on the
host for the Docker-based workflow.

### Environment configuration

Create `.env` from the example:

``` bash
cp .env.example .env
```

The local environment uses separate PostgreSQL databases:

``` text
tasks       -> development
tasks_test  -> automated tests
```

Expected database configuration includes:

``` env
DATABASE_HOST=db
DATABASE_PORT=5432
DATABASE_NAME=tasks
DATABASE_TEST_NAME=tasks_test
DATABASE_USER=tasks_user
DATABASE_PASSWORD_FILE=/run/secrets/db_password

POSTGRES_DB=tasks
POSTGRES_USER=tasks_user
```

### Local secret

Create the PostgreSQL password file:

``` bash
mkdir -p secrets
printf '%s\n' 'your-local-password' > secrets/db_password.txt
chmod 600 secrets/db_password.txt
```

Do not commit this file.

Docker Compose mounts it inside the containers as:

``` text
/run/secrets/db_password
```

Docker Compose secrets are appropriate for this local environment, but
they are not a production secret manager.

## Database Migrations

Alembic manages schema changes.

Apply all pending migrations:

``` bash
make migrate
```

Rollback the latest migration:

``` bash
make downgrade
```

Create a new autogenerated migration:

``` bash
docker compose run --rm api \
  alembic revision --autogenerate -m "migration name"
```

Review generated migrations before applying them.

Migrations are deliberately not executed automatically when the API
starts. This avoids multiple application replicas attempting to modify
the schema simultaneously.

## Tests

Run the complete test suite:

``` bash
make test
```

The project separates tests by purpose:

``` text
tests/
├── unit/
│   └── test_health.py
└── integration/
    └── test_tasks.py
```

The integration tests exercise the API, service layer, SQLAlchemy, and
PostgreSQL.

A dedicated database is used for tests:

``` text
tasks       -> development
tasks_test  -> testing
```

Tests override FastAPI's database dependency so integration tests do not
operate on development data.

## Coverage

Run:

``` bash
make coverage
```

Coverage reports which application code is executed by the tests and
highlights untested lines.

Coverage is a supporting quality metric, not a guarantee that the
application is correct. Tests should verify meaningful behavior rather
than target 100% coverage for its own sake.

## Dependency Management

Dependencies are declared in:

``` text
pyproject.toml
```

Exact resolved versions are recorded in:

``` text
uv.lock
```

The lock file should be committed to Git to make application builds
reproducible.

Add a runtime dependency with:

``` bash
uv add <package>
```

Add a development dependency with:

``` bash
uv add --dev <package>
```

After dependency changes, rebuild the Docker image:

``` bash
make build
```

## Secrets

### Local development

Local Docker Compose uses a file-backed secret:

``` text
secrets/db_password.txt
        |
        v
Docker Compose secret
        |
        v
/run/secrets/db_password
```

The secret file must remain excluded from Git and from the Docker build
context.

### Production

Do not use a plaintext repository file as the production secret source.

A production Kubernetes environment should use an external
secret-management solution such as:

-   HashiCorp Vault
-   AWS Secrets Manager
-   Google Secret Manager
-   Azure Key Vault

A Kubernetes deployment can integrate these systems using a solution
such as External Secrets Operator.

## Production / Kubernetes Roadmap

Docker Compose is the local development environment.

The target production architecture is:

``` text
Internet
   |
   v
Gateway API / Ingress
   |
   v
Kubernetes Service
   |
   v
FastAPI Deployment
   |
   v
Managed PostgreSQL
```

The production implementation should include:

-   immutable application image published to a container registry
-   multiple FastAPI replicas
-   Kubernetes Deployment and Service
-   Gateway API or Ingress
-   liveness and readiness probes
-   CPU and memory requests/limits
-   Horizontal Pod Autoscaler where appropriate
-   managed PostgreSQL
-   ConfigMaps for non-sensitive configuration
-   external secret management
-   least-privilege database credentials
-   separate database credentials for application DML and migrations
    where appropriate
-   Alembic migrations executed as a dedicated deployment Job or CI/CD
    step
-   centralized logs and metrics
-   container and dependency security scanning
-   GitOps with Argo CD or Flux where appropriate

## Development Principles

This project intentionally follows a few simple principles:

-   keep API routes thin
-   keep business logic in the service layer
-   validate external data with Pydantic
-   manage schema changes with Alembic
-   keep secrets outside source control
-   use reproducible dependency locking
-   test behavior against an isolated database
-   automate repetitive developer operations
-   keep database migrations separate from application startup
-   design the local project so it can evolve naturally toward
    Kubernetes and CI/CD
